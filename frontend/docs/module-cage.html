Cage generation: the main objective

This is the end goal of the thesis. Prediction tasks were preparation; here I try to construct valid (k,g)-graphs and check how close I am to cage-size solutions.

Why A* first?

A* gives controlled symbolic search with hard constraints. In this implementation, it is a best-first search over partial graph states, not a shortest path between two vertices. The start state is moore_bound(k,g) isolated vertices; expansions add constraint-safe edges (or occasionally a vertex), and candidates are ranked by heuristic score.

Here, Moore bound is the theoretical lower bound on the number of vertices needed for a (k,g)-graph. 

# ai/cage/functions/astar.py
for succ_graph in successors:
    graph_h = graph_hash(succ_graph)
    if graph_h in self.visited_hashes:
        self.duplicates_skipped += 1
        continue
    self.visited_hashes.add(graph_h)
    succ_score = self._score_graph(succ_graph)
    heapq.heappush(self.pq, (-succ_score, self.counter, succ_graph))

Why RL on top of that?

RL was added as a guide policy: bias search toward promising actions. The environment acts on unordered node pairs; existing edges can be removed, missing edges can be added if constraints allow it.

Reward semantics in the current code are: add valid edge +0.1, remove -0.2, invalid add -1.0, dead-end -2.0, success 10.0 + 0.5*g, with termination guards for max steps and score floor.

How is runtime behavior controlled?

Generation is session-based and isolated per request. The backend caps concurrency at MAX_PARALLEL_GENERATIONS = 3; when full, it returns HTTP 429. This keeps API behavior stable under multiple users.
